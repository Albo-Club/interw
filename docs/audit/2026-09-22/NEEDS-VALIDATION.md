# Needs validation — prioritized leads without severity

Each lead is source-grounded, but its decisive fact is outside the repository or could not be observed offline (no node_modules, no deployment). None is a confirmed vulnerability. Plans are bounded local fixtures or owner-observed configuration checks; none sends audit traffic to a deployment.

## Pre-hijack: an attacker-registered, unverified password account for the victim's address can become the victim's identity once any trusted method verifies that address

Fingerprint: `convex/auth.ts:createAuth:unverified-credential-account-merge`

Signup is open and unauthenticated: anyone can POST /api/auth/sign-up/email (proxied verbatim at src/routes/api/auth/$.ts:29) with victim@example.com and a password of the attacker's choosing. Better Auth persists the user with emailVerified=false plus a credential account; requireEmailVerification (convex/auth.ts:105) blocks the attacker's sign-in but nothing in this repository ever removes, rejects or even reads that unverified credential account -- `emailVerified` is written in exactly one place (convex/auth.ts:209) and read nowhere. When the real owner arrives, typically through an org invitation, invitations.preview reports accountExists=true (convex/invitations.ts:124) and /accept-invite therefore renders SignInToAccept (src/routes/accept-invite.$token.tsx:143), which offers only a password field the victim does not know and a magic-link button; no fresh sign-up path exists on that card. If the magic-link plugin (disableSignUp, convex/auth.ts:298) resolves the attacker-created user, opens a session on it and marks it verified, provisionAppUser (convex/lib/auth.ts:49) binds the Convex users row to that BA user and invitations.accept inserts the org membership on it (convex/invitations.ts:179); the attacker then signs in with the address and the password they chose and holds the victim's Convex identity and org memberships. A second completion needs no magic link at all: sendOnSignUp (convex/auth.ts:139) already mails the victim a 'Verify your email ... You'll be signed in automatically' link (convex/emailTemplates.ts:312-313) whose footer says 'If you didn't create an account, you can safely ignore this email', and per the vendored official Better Auth skill the same mail is re-sent on every unverified sign-in attempt, so the attacker can re-deliver it on demand within the verificationSend bucket; one victim click flips the flag on the attacker's account. With Google enabled, accountLinking.enabled without trustedProviders (convex/auth.ts:178-182) is the OAuth variant of the same merge. What remains unproven offline is whether Better Auth actually performs any of those three transitions on a user whose emailVerified is false.

**Claimed root cause.** convex/auth.ts enables three ways to prove an address (password + verification mail, magic link, optional Google) but treats the unverified password account an arbitrary caller created as the same identity a later mailbox-proving method lands on. The invariant the repository documents at KNOWN_ISSUES.md:59 -- 'the attacker's password account stays unverified, so BA refuses to link it' -- holds only if every trusted method refuses to sign into, verify or link into an existing unverified user; no hook in this repository (databaseHooks.user.create.before, user.update.after, sendMagicLink) enforces that, and provisionAppUser's email fallback (convex/lib/auth.ts:56-65) explicitly assumes every BA user email is verified and unique.

### Affected boundary

BA verified-email invariant + invite predicate + syncBetterAuthUser

### Trace

1. **entrypoint** `convex/auth.ts:104` — createAuth.emailAndPassword: Password sign-up is enabled for any address with no invitation or allow-list gate; the BA user and its credential account are created by whoever submits the form, reachable unauthenticated through the proxy at src/routes/api/auth/$.ts:29.
2. **propagation** `convex/auth.ts:105` — createAuth.emailAndPassword.requireEmailVerification: requireEmailVerification blocks the attacker's own sign-in but leaves the user row and credential account in place; this is the single control the whole chain has to defeat.
3. **propagation** `convex/auth.ts:139` — createAuth.emailVerification.sendOnSignUp: The victim is mailed a generic 'Verify your email' link at the moment the attacker registers their address (convex/emailTemplates.ts:310-321).
4. **propagation** `convex/auth.ts:140` — createAuth.emailVerification.autoSignInAfterVerification: Clicking that link is advertised to sign the clicker in automatically -- into the attacker-created user, since that is the only user holding the address.
5. **propagation** `convex/auth.ts:298` — createAuth.plugins.magicLink: disableSignUp restricts magic links to users that already exist -- the attacker-created user qualifies; sendMagicLink (299-315) mails the address without inspecting emailVerified or the presence of a foreign credential account.
6. **propagation** `convex/invitations.ts:124` — invitations.preview: accountExists is computed from the Better Auth user table by email (119-123) and is true for the attacker-created user.
7. **propagation** `src/routes/accept-invite.$token.tsx:143` — AcceptInvitePage: accountExists routes the invitee to SignInToAccept (239-373): a read-only email field, a password the victim does not know (325-350) and a magic-link button (358-367) wired to authClient.signIn.magicLink (274-286). No sign-up branch is offered once an account exists.
8. **propagation** `convex/lib/auth.ts:49` — provisionAppUser: Whatever BA session the victim ends up with resolves to the attacker-created BA id; the Convex users row is created for it, or an existing row is re-pointed to it through the by_email fallback (56-65).
9. **propagation** `convex/invitations.ts:179` — invitations.accept: organizationMembers is inserted for that shared user after the email-match check passes (175-177) -- the addresses do match, because both principals are the same BA user.
10. **sink** `convex/auth.ts:103` — createAuth.emailAndPassword sign-in: Once emailVerified is true on that user, sign-in/email with the address and the attacker's chosen password is accepted and the session carries the victim's Convex identity, org memberships and role.

### Verified evidence

- `convex/auth.ts:209` — The only write of emailVerified in the entire repository (token-gated invite pre-verification). A repo-wide grep for `emailVerified` returns this line and the comment above it and nothing else: no code path removes, flags or refuses an unverified credential account, and nothing reads the flag before linking or provisioning.
- `KNOWN_ISSUES.md:59` — 'Verified email closes the hole : the attacker's password account stays unverified, so BA refuses to link it.' The repository's stated threat model (53-60 describes exactly this attacker) rests entirely on a Better Auth behaviour it never verifies in code.
- `convex/auth.ts:180` — accountLinking.enabled with no trustedProviders: the Google variant of the merge, where a verified Google identity for the same address would link into the existing unverified user.
- `convex/emailTemplates.ts:313` — The verification mail tells the recipient 'If you didn't create an account, you can safely ignore this email' while line 312 promises 'You'll be signed in automatically' -- a victim who did not register has no signal that the account is foreign and clicking is the advertised action.
- `.agents/skills/email-and-password-best-practices/SKILL.md:41` — Vendored official Better Auth skill (pinned in skills-lock.json to better-auth/skills@20c9e88): with requireEmailVerification enabled, 'unverified users will receive a new verification email on each sign-in attempt'. The attacker can therefore re-deliver the verification mail to the victim at will, without the victim ever touching a magic link.
- `convex/rateLimiters.ts:18` — verificationSend bounds those mails per recipient address (capacity 3, 5/h) but bounds nothing about the single click that completes the takeover.
- `src/routes/register.tsx:80` — The product's own sign-up surface is unauthenticated and takes an arbitrary email; nothing upstream of Better Auth restricts which address may be registered.

### Exact blockers

- better-auth@1.6.30 is not installed (node_modules absent, installation prohibited): whether the magic-link verify handler signs a session for an existing user whose emailVerified is false -- and whether it sets emailVerified=true on that user -- must be read from node_modules/better-auth/dist/plugins/magic-link. If it refuses unverified users the primary chain dies at the invite card; if it verifies them the takeover completes with no victim action beyond using the invitation.
- Whether GET /verify-email sets emailVerified=true on an existing unverified user and, with autoSignInAfterVerification, opens a session on it (node_modules/better-auth/dist/api/routes/verify-email). This is the second, magic-link-free completion: the mail is already sent at sign-up and re-sent on each of the attacker's sign-in attempts, so only this transition is unproven.
- For the Google variant: whether handleOAuthUserInfo links a verified provider identity into an existing user whose emailVerified is false when accountLinking.enabled is set with no trustedProviders, and whether it updates that user's emailVerified on link (node_modules/better-auth/dist/oauth2/link-account).

### Resolution plans

(b) Then a vitest, entirely in-process against a memory adapter and dummy @test.local addresses, with betterAuth({ database: memoryAdapter(), emailAndPassword: { enabled: true, requireEmailVerification: true, minPasswordLength: 12 }, emailVerification: { sendOnSignUp: true, autoSignInAfterVerification: true, sendVerificationEmail: capture }, account: { accountLinking: { enabled: true } }, plugins: [magicLink({ disableSignUp: true, sendMagicLink: capture })] }): step 1 signUp.email('victim@test.local', 'attacker-password-12'); assert user.emailVerified === false and a credential account exists. ## Transactional email templates interpolate the action URL raw into HTML; a caller-shaped Better Auth redirectTo/callbackURL would inject markup into first-party reset, verification and magic-link emails

Fingerprint: `convex/emailTemplates.ts:layout:cta-url-unescaped`

convex/emailTemplates.ts escapes every user-supplied string with esc() but writes the `url` argument unescaped into href="${cta.url}" in layout() and as raw inner HTML in urlFallback(). For resetPasswordEmail, verificationEmail and magicLinkEmail (and, on the same layout, changeEmailVerificationEmail and deleteAccountVerificationEmail) that url is Better Auth's data.url, which BA assembles from the request's redirectTo / callbackURL. Independently reproduced locally against the real module: rendering the three templates with url = 'https://app.example/api/auth/reset-password/TOK?callbackURL=https://app.example/"><a href="https://evil.example/login">Reactivate your account</a><span style="display:none' yields HTML containing three <a href=...> elements instead of one, including a verbatim attacker anchor next to the genuine button, with no &quot; encoding anywhere on the url; the same value passed through esc() first leaves exactly one anchor and no injected markup. Two in-repo routes would feed such a string to Better Auth: an anonymous POST to /api/auth/forgot-password, /api/auth/send-verification-email or /api/auth/sign-in/magic-link through the verbatim proxy at src/routes/api/auth/$.ts, and the app's own /login?redirect= parameter, which internalRedirectSearch accepts without normalising (verified locally: '/"><a href="https://evil.example">x</a>' passes isInternalPath and is returned verbatim) and login.tsx hands to authClient.sendVerificationEmail as callbackURL. The victim would receive a DKIM-authenticated first-party email whose HTML carries attacker-chosen links and text — phishing with the application's own sender reputation. What is not source-visible is the middle leg: whether better-auth 1.6.30 percent-encodes that parameter when building data.url, and whether its origin check tolerates '"', '<' and '>' in a same-origin or rooted value.

**Claimed root cause.** layout() (convex/emailTemplates.ts:41) and urlFallback() (line 110) treat the `url` argument as safe HTML while the Better Auth senders in convex/auth.ts (lines 111-124, 141-154, 299-307) pass a URL that embeds a caller-supplied redirect parameter; trustedOrigins is an origin comparison, not a character filter, and the templates apply esc() to every other interpolated value but not to url.

### Affected boundary

esc() on HTML branches; raw subjects; Resend HTTP API

### Trace

1. **entrypoint** `src/routes/api/auth/$.ts:29` — Route.server.handlers.ANY: Anonymous POST to /api/auth/forgot-password (also /send-verification-email and /sign-in/magic-link) carrying a caller-chosen redirectTo / callbackURL in the body; the handler proxies method, headers and body unchanged to the Better Auth routes.
2. **propagation** `convex/auth.ts:111` — createAuth > emailAndPassword.sendResetPassword: Better Auth invokes the sender with data.url assembled from that request. The only in-repo controls are trustedOrigins: [siteUrl] (line 49), the BA rule '/forgot-password': 3 per 60 s (line 62) and the per-email application limit consumed at line 116.
3. **propagation** `convex/auth.ts:124` — sendResetPassword: `url: data.url` is forwarded verbatim into resetPasswordEmail; the identical pattern reaches verificationEmail at line 154 and magicLinkEmail at line 307.
4. **propagation** `convex/emailTemplates.ts:393` — resetPasswordEmail: url is placed into the body paragraphs via urlFallback(locale, url) and into the call-to-action at line 394 (`cta: { label: c.cta, url }`), with no esc() applied to it at either site.
5. **sink** `convex/emailTemplates.ts:41` — layout > ctaHtml: `<a href="${cta.url}"` — a url containing '"><a …>' closes the href attribute and injects arbitrary markup into the HTML body of the outgoing DKIM-signed email; urlFallback (line 112) additionally writes the same url as raw inner HTML inside a <span>.

### Verified evidence

- `convex/emailTemplates.ts:97` — esc() is defined here and applied to inviterName, orgName, candidateName, jobTitle, recommendation, newEmail, email and name in every HTML branch — re-verified locally by rendering invitationEmail with '<b>X</b>' and '"><img src=x onerror=1>', both of which come back entity-encoded — but it is never applied to `url`.

- `convex/auth.ts:299` — sendMagicLink forwards the Better Auth-built url to magicLinkEmail at line 307; disableSignUp: true on line 298 means the victim must already hold an account for the magic-link and reset variants.
- `src/routes/login.tsx:110` — The application itself hands the ?redirect= search param straight to authClient.sendVerificationEmail as callbackURL, so a crafted /login?redirect=… link is a second, first-party way for attacker characters to reach Better Auth's URL assembly.

## 300 MiB per-answer uploads reach a transcription action that buffers the whole object and a 5-slot pool shared by every tenant

Fingerprint: `convex/interview.ts:MAX_SEGMENT_BYTES:exceeds-transcribe-buffering`

A candidate holding a link may presign each answer up to MAX_SEGMENT_BYTES = 300 MiB: validateMedia accepts any positive integer content length up to that bound and requestSegmentUpload signs it into the PUT, so the browser can legitimately upload an object of that size per question. Nothing on the server ties an answer's byte size or duration to the recruiter's question.maxResponseSeconds, and markSegmentUploaded accepts whatever durationSeconds the client reports. After finish, onSessionCompleted enqueues transcribeSegment per uploaded answer; that action streams the object out of the bucket and materialises it entirely with new Response(stream).blob() before posting it to the provider with a 300 s timeout, in the default Convex runtime (convex/pipeline.ts carries no 'use node' — only convex/jobImportFetch.ts does). Failures are rethrown so the workpool retries, up to 4 attempts per segment, on mediaPool with maxParallelism 5, which the workpools comment notes is a deployment-wide ceiling shared by every organisation. Which of two outcomes follows is not decidable from the repository: if the runtime's action memory ceiling is below the buffered object the job fails on every attempt while holding shared pool slots for other tenants, and if it is not, the operator pays for provider transcription of arbitrary-length audio chosen by a token holder.

**Claimed root cause.** MAX_SEGMENT_BYTES is sized for a video container, but the same bound governs the audio object that is later transcribed, and no server-side check relates an answer's size or duration to question.maxResponseSeconds before paid, pooled work is enqueued; convex/lib/ai.ts:transcribe then buffers the whole object in memory rather than streaming it to the provider.

### Affected boundary

per-token rate limits and per-session row caps

### Trace

1. **entrypoint** `convex/interview.ts:330` — requestSegmentUpload (public action, args { token, questionIndex, audio, video }): Public, token-authenticated action; the caller states audio.contentLength and video.contentLength.
2. **propagation** `convex/interview.ts:222` — validateMedia: The only size check: contentLength must be a positive integer no greater than MAX_SEGMENT_BYTES (300 MiB), applied to audio and video alike.
3. **propagation** `convex/interview.ts:351` — requestSegmentUpload, presignPut: The accepted content length is signed into the PUT URL, so the client may transfer exactly that many bytes into the bucket.
4. **propagation** `convex/interview.ts:510` — finish: Schedules internal.pipeline.onSessionCompleted once the candidate finishes.
5. **propagation** `convex/pipeline.ts:160` — onSessionCompleted, mediaPool.enqueueAction: One transcribeSegment job per uploaded answer is enqueued on the deployment-wide media workpool.
6. **propagation** `convex/pipeline.ts:266` — transcribeSegment: getObjectStream(key) opens the stored object; the failure path at 296 rethrows so the pool retries the same input.
7. **sink** `convex/lib/ai.ts:169` — transcribe: new Response(stream).blob() materialises the entire object in the action's memory before it is posted to the provider as multipart form data.

### Verified evidence

- `convex/interview.ts:38` — MAX_SEGMENT_BYTES = 300 * 1024 * 1024, applied by validateMedia to the audio track and the video container alike.
- `convex/interview.ts:400` — markSegmentUploaded stores whatever durationSeconds the client reports (only rounded and floored at zero); no server-side duration bound exists anywhere on this path.
- `convex/questions.ts:89` — question.maxResponseSeconds is validated when the recruiter sets it, but it is only ever read as prompt context (convex/pipeline.ts:473, 619) and never enforced against an uploaded answer.
- `convex/lib/objectStore.ts:149` — presignPut signs content-length when given, so the signed value is the real ceiling on the transfer — and it is the value the caller proposed, up to 300 MiB.
- `convex/lib/objectStore.ts:210` — getObjectStream fetches the object and returns response.body; there is no range read, size check or truncation anywhere in the module.
- `convex/lib/ai.ts:75` — TRANSCRIPTION_TIMEOUT_MS = 300_000: each attempt may hold its pool slot for five minutes.
- `convex/lib/workpools.ts:17` — RETRY = { maxAttempts: 4, ... } — four attempts per segment on the same oversized input.
- `convex/lib/workpools.ts:26` — mediaPool maxParallelism 5, and the comment states the parallelism cap is per deployment across every pool — the shared resource every organisation draws on.
- `convex/pipeline.ts:234` — transcribeSegment is an internalAction in convex/pipeline.ts, which carries no 'use node' directive (only convex/jobImportFetch.ts:1 does), so it runs in the default Convex runtime.
- `convex/pipeline.ts:296` — The catch rethrows deliberately so the pool retries, which is what turns a single oversized object into four attempts.

### Exact blockers

- The default Convex runtime's per-action memory ceiling, and its behaviour when an action exceeds it, are not stated anywhere in the repository; convex/_generated/ai/guidelines.md documents transaction limits, the 1 MB value/document size limit and pagination limits, but no action memory bound. Whether buffering a 300 MiB object throws, is killed, or succeeds is therefore unknown from source.
- The transcription provider's maximum accepted file size and audio duration, and its per-audio-second pricing, are external facts. Which of the two outcomes occurs — repeated failure that occupies shared pool slots, or successful paid transcription of candidate-chosen length — depends entirely on that, and the two have different impacts.
- The path cannot be exercised locally: the sandbox has no network, node_modules is absent and installation is prohibited, and a Node harness cannot reproduce the memory behaviour of the Convex V8 runtime or the provider's acceptance rules. Only the source-visible bounds (validateMedia, presignPut, pool configuration) were re-verified.

### Resolution plans

- **Owner-observed deployment**: Owner-observed on a non-production Convex deployment with test provider credentials, with no traffic sent to production. Invite a dummy candidate to a dummy role with one question, reserve a segment through requestSegmentUpload declaring a ~250 MiB audio contentLength, PUT a silent audio file of exactly that size to the signed URL, mark it uploaded, and call finish. Then read, in the Convex dashboard: the jobLog rows for step 'transcribe' (outcome, attempt, durationMs, audioSeconds and error text on each of the up to four attempts), the deployment logs for the transcribeSegment action to see whether it terminates on a memory limit and at what size, the mediaWorkpool queue depth and slot occupancy while those attempts run, and the provider's own dashboard for whether the request was rejected for size or length and how many audio seconds were billed. Repeat with a small answer as the control. The decisive facts to record are: the largest object size transcribeSegment completes without a runtime memory failure, the provider's stated maximum file size and duration, and the billed seconds for an oversized answer.

## Job-ad fetch validates the addresses dns.lookup returns but lets fetch resolve the hostname again, leaving a DNS-rebinding window to loopback and link-local targets

Fingerprint: `convex/jobImportFetch.ts:fetchJobPage:dns-check-then-fetch-reresolves`

fetchJobPage validates every hop twice: lexically through assertPublicHttpUrl (convex/lib/safeUrl.ts) and then by resolving the hostname with dns.lookup(..., { all: true }) and rejecting any private answer (convex/jobImportFetch.ts:56-71, called at 115). It then calls global fetch on the same URL (117) with no dispatcher, agent or lookup override — I grepped convex/ and src/ and found no setGlobalDispatcher, no undici Agent and no dns.setDefaultResultOrder anywhere — so undici performs its own resolution when it connects. A hostname served by an attacker-controlled resolver with TTL 0, alternating a public address with 127.0.0.1 or 169.254.169.254, can therefore pass the check and be connected to at a private address. The source states the gap in two places (jobImportFetch.ts:24-26 and safeUrl.ts:16-19) and attributes it to fetch not letting the connection be pinned; that is true of the WHATWG fetch options, but Node's undici does accept an Agent with connect.lookup, so the gap is closable in this stack. The channel is readable, not just reachable: the reply is accepted only if it is 2xx with content type text/html, application/xhtml+xml or text/plain (152), and its body is then summarised by a model and returned to the recruiter as a draft (convex/jobImport.ts:86-111). What cannot be settled from source is whether the deployed Convex Node runtime's resolver actually re-resolves between the check and the connect (a cache honouring a minimum TTL would close the window in practice), and what, if anything, answers on loopback or link-local from that runtime with an allow-listed content type. Without those two facts there is no observable result, only a race that the code shape permits.

**Claimed root cause.** The address that passed the private-range check is not the address the request is sent to: assertResolvesPublicly (convex/jobImportFetch.ts:56-71) and fetch (convex/jobImportFetch.ts:117) resolve the hostname independently, so the guard is a time-of-check/time-of-use race against a DNS record the requester controls. The same applies to each redirect hop, which is re-validated (130) and then re-fetched the same way.

### Affected boundary

assertPublicHttpUrl + assertResolvesPublicly per hop + size/content-type caps

### Trace

1. **entrypoint** `convex/jobImport.ts:60` — importFromUrl action: Public Convex action taking a caller-supplied `url` string; authorises via requireProjectEditable and the per-user jobImport limiter, then passes the URL to the Node fetcher at line 76. The caller chooses the hostname, hence the DNS record behind it.
2. **propagation** `convex/jobImportFetch.ts:115` — fetchJobPage hop loop: assertResolvesPublicly(current) is awaited before each hop; it rejects a literal private host (58) and every address returned by lookup(url.hostname, { all: true }) that is private (61-70). The resolved addresses are checked and then discarded — nothing carries them forward.
3. **propagation** `convex/jobImportFetch.ts:117` — fetchJobPage hop loop: fetch(current, { redirect: 'manual', signal, headers }) — the connection. No dispatcher or lookup binds it to the addresses just checked, so undici resolves the hostname again and connects to whatever it answers with at that moment.
4. **sink** `convex/jobImport.ts:88` — importFromUrl handler: Whatever the connection returned, once it passed the 2xx and content-type gates, becomes pageText and is sent to the model, whose draft is returned to the recruiter — which is what would make a successful rebind a read primitive rather than a blind one.

### Verified evidence

- `convex/jobImportFetch.ts:24` — Author comment: 'What none of this closes: an attacker who controls a DNS record and moves it between our resolution and our connection. Fixing that means connecting to the address we checked, which `fetch` does not let us choose.'
- `convex/jobImportFetch.ts:61` — `addresses = await lookup(url.hostname, { all: true })` — the checked resolution; its results are only iterated over at 68-70 and never reused for the connection.
