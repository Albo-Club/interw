# Security audit report — interw (Albo-Club/interw)

## 1. Run summary

- **Run**: interw-run-1-2026-09-22; source ref 9a70f3f (branch checkout of origin/main, worktree clean).
- **Profile**: started as `standard`, switched to `quick` after the wave-1 hunters were launched (user request, cost). Consequences: exactly one final coverage-critic pass, one fresh independent verifier per candidate performing both candidate validation and final-record verification, and no second hunter wave. The evidence bar was not lowered. **This is therefore a partial pass**, not a claim of complete coverage.
- **Scope**: whole repository (convex/, src/, scripts/, .github/, build and dependency manifests). No budget was set. Agents spent: 4 reconnaissance, 12 hunters, 1 critic, 10 verifiers (27 total).
- **Execution policy**: sandboxed source-and-local-only. No deployment, provider, registry, or shared service was contacted. `node_modules` was absent and installation is prohibited, so every local check ran dependency-free modules (or the real Convex handlers under stub loaders for `convex/values`, `convex/server`, `_generated/*` and the mounted components) under an OS sandbox: new mount+network namespace with no interfaces, read-only target, scratch-only writes, empty environment, prlimit and a 60 s wall clock. Better Auth, the Convex components and Streamdown could not be read, which is why several leads remain `needs_validation`.
- **Prior runs**: none compatible. A hand-written review (`docs/audit/2026-09-15/`) was used as reconnaissance input only; nothing was carried, excluded, or revalidated from it.
- **Deferred coverage** (critic-accepted, not assigned under the quick profile): (1) the Better Auth route family mounted on the Convex site origin (`<deployment>.convex.site`) and its CORS/cookie/Origin policy; (2) the trustworthiness of the CI access-audit script itself (`scripts/audit-convex-access.mjs`), which recognises only `ctx.db`/`ctx.scheduler` writes and truncates some handler bodies. One unit is **blocked**: the Resend webhook (`/resend-webhook`) on the `@convex-dev/resend` component internals (fail-closed on a missing secret, replay window). No unit was out of scope.

## 2. Security posture

The authorization core is sound: every recruiter function reads the organisation off the row it acts on, candidate and share tokens fail identically when unresolved, projectors and runtime `returns` validators keep rows away from token holders, object keys are derived server-side and re-derived on attach, signed URLs are minted only after an access check, and the agent's tools re-derive membership from the thread scope. No cross-tenant read or write, no authentication bypass, and no injection into an HTML or command sink was found. What the audit did find is a consistent second-tier pattern: a control implemented in one place and skipped by a sibling path — the candidate gate that `finish` does not consult, the chat limiter that the HTTP route omits, the project-visibility filter that two org-scoped reads lack, the archive tier that `restore` does not share, the erasure set that a re-reservation silently shrinks, and a candidate-supplied number presented to recruiters as a measurement. Ten findings were confirmed by independent reproduction on the unmodified handlers; five are medium, five low, none high or critical. Ten leads are blocked on library or deployment facts that could not be observed offline, and one candidate was rejected.

### MEDIUM — POST /api/chat skips the per-user chatSend rate limiter that every other chat-generation path enforces, giving any org member unmetered paid model calls and unbounded agent-thread creation

Fingerprint: `convex/chat.ts:streamOverHttp:chatSend-limiter-bypass`

- **Source location**: `convex/http.ts:31` (entrypoint) → `convex/chat.ts:275` (propagation) → `convex/chat.ts:287` (propagation) → `convex/chat.ts:294` (propagation) → `convex/chat.ts:300` (sink)
- **Lower-trust principal**: Caller holds a valid Convex bearer JWT for a Better Auth account. Signup is self-service: email+password with requireEmailVerification (convex/auth.ts:103-105), plus invitation and optional Google.
- **Conditions**: authentication_level: Caller holds a valid Convex bearer JWT for a Better Auth account. Signup is self-service: email+password with requireEmailVerification (convex/auth.ts:103-105), plus invitation and optional Google. · authorization_role: Caller is a member of any role of the organisation named in the request body. Any registered user can satisfy this by creating their own organisation, which makes them its owner (convex/organizations.ts:74-105). · system_configuration: ANTHROPIC_API_KEY is configured on the Convex deployment so chatAgent.streamText reaches the provider; the route is registered unconditionally in convex/http.ts, with no feature flag. · third_party_dependency: The only remaining bounds are outside the repository: Convex per-deployment HTTP-action concurrency and body limits, and the Anthropic account's rate and spend limits. These throttle the deployment as a whole rather than the abusing user, so when they bite they degrade chat for every tenant.
- **Bounded reproduction** (target-native, no deployment contacted): An authenticated member of any organisation, including one it created for itself moments earlier, sends repeated JSON POSTs to https://<deployment>.convex.site/api/chat carrying the Convex bearer token the SPA already holds. Each request yields a new durable agent thread and a full agent generation, and none of them is counted against the chatSend bucket that caps the same action in the product UI.
  - Inputs: `POST /api/chat  Authorization: Bearer <convex-jwt>  Content-Type: application/json  {"orgId":"<an org the caller belongs to>","prompt":"prompt 0"}`; `the same request repeated N times with no threadId field (verifier harness used N=5) -- each one creates a thread and a paid model call`; `{"orgId":"<own org id>","prompt":"<307200-byte string>"} -- accepted, forwarded to the model with no app-level prompt cap`
- **Actual result**: Case 1 anonymous: 401, 0 threads, 0 model calls. Case 2: five 200 responses with X-Thread-Id thread_1..thread_5; limiterCalls 0, threadsCreated 5, paidModelCalls 5, each agent call logged as createThread + PAID_MODEL_CALL under scope 'org_A:users_A'. Case 3 control: sendMessage on thread_1 recorded limiterCalls [{name:'chatSend', key:'users_A'}] and scheduled chat:streamAsync. Case 3b control: respondToToolApproval recorded the same chatSend consumption. Case 4 non-member: ConvexError not_a_member with 0 threads and 0 model calls. Case 5 foreign-scope threadId: ConvexError forbidden with 0 model calls. Case 6: 200 with the model call receiving promptBytes 307200 and 0 limiter calls. Case 7 malformed JSON: SyntaxError thrown after authentication, nothing reached. Case 8 missing prompt: 400, nothing reached. Total limiter calls recorded across every streamOverHttp invocation in the run: 0. This independently reproduces the hunter's result: membership and thread-scope enforcement hold, the per-user budget does not.
- **Impact**: An explicit security control is fully defeated on this path -- locally observed as five paid model calls against zero limiter consumptions, versus one consumption on the control path -- but what it protects is operator cost and shared capacity, not data or privilege. Each unmetered request is worth up to ten model steps (convex/agent.ts:23) on an unbounded prompt and leaves one new durable agent thread with its messages behind. The blast radius reaches other tenants only indirectly, when the shared Anthropic key or the deployment's action concurrency throttles. Authentication, org membership and thread scoping all held under test, so there is no disclosure and no privilege gain.
- **Priority rationale**: likelihood medium — The prerequisites are cheap and entirely self-service: a verified email+password account (convex/auth.ts:103-105), an organisation the caller creates for itself in one unmetered mutation (convex/organizations.ts:74-105), and the bearer token the SPA already holds. The route sits on the public .convex.site origin at a conventional path and is registered unconditionally. It is not, however, exercised by any client code, so an attacker has to look for it rather than stumble on it; the repository's own prior review already recorded the same gap (docs/audit/2026-09-15/pipeline-ia-stockage.md:772-782), which corroborates that it is a real and findable surface. Overall medium (never above demonstrated impact medium). Confidence high.
- **Smallest source fix**: Preferred: delete the route -- nothing under src/ calls it, and the in-app path (sendMessage + listMessages) already covers the product. If it must stay, make it pay the same budget as the mutation paths rather than trusting a second door: turn actionAuthProbe into an internalMutation that performs requireOrgMember and consumeLimit('chatSend', user._id) as one unit and is called with ctx.runMutation, so the limiter is structurally inseparable from the membership check instead of being a call someone can forget again; additionally validate the body (it is currently a bare cast, chat.ts:278-282), cap prompt length, and require an existing threadId rather than minting a durable thread per request. Regression test: load convex/chat.ts with @convex-dev/rate-limiter and @convex-dev/agent mocked and assert that streamOverHttp records a limit('chatSend', <userId>) call before any streamText call, mirroring the assertion for sendMessage -- the harness in this verification is a working template for it. Note for the reviewer: fixing this does not remove the need for a bound on organizations.create, which is itself unmetered and is what makes the membership precondition free to satisfy.

- **Source location**: `convex/interview.ts:481` (entrypoint) → `convex/interview.ts:490` (propagation) → `convex/interview.ts:491` (propagation) → `convex/interview.ts:497` (propagation) → `convex/interview.ts:504` (propagation) → `convex/interview.ts:506` (propagation) → `convex/interview.ts:510` (propagation) → `convex/pipeline.ts:119` (propagation) → `convex/pipeline.ts:160` (propagation) → `convex/pipeline.ts:267` (propagation) → `convex/pipeline.ts:600` (propagation) → `convex/notifications.ts:109` (sink)
- **Lower-trust principal**: Attacker holds a candidate session access token (the invited candidate, or anyone the invitation email was forwarded to). No account and no other credential.
- **Conditions**: authentication_level: Attacker holds a candidate session access token (the invited candidate, or anyone the invitation email was forwarded to). No account and no other credential. · authorization_role: A project owner or admin previously called sessions.cancel on that session, or archived the role / left it in draft — the recruiter decision being overridden. · data_state: Session status is anything but 'completed' ('cancelled', 'expired', 'pending' or 'in_progress'). At least one segment in uploadState 'uploaded' is needed for provider spend and the email; with zero segments the status flip, the retention reset and the counter increment still happen.

The session becomes a completed interview, the pipeline runs on whatever was uploaded before the cancellation, and the organisation is emailed a report for a candidate it withdrew.
  - Inputs: `api.interview.finish({ token: "<accessToken of a session whose status is 'cancelled'>" })`; `api.interview.finish({ token: "<accessToken of an in_progress session whose project.status is 'archived'>" })`; `dummy session { status: 'cancelled', lastQuestionIndex: 1, consentAcceptedAt: 1 } with project { status: 'active' } passed to evaluateSessionGate for comparison`
- **Actual result**: Check A (target gate): cancelled/active -> state=cancelled canRecord=false; in_progress/archived -> closed; in_progress/draft -> closed; expired/active -> expired; in_progress/active control -> resumable canRecord=true. Check B (unmodified finish handler): status=cancelled -> no throw, returned {"alreadyCompleted":false}, status cancelled->completed, purgeAfter 15811200000->now+31536000000, completedSessionCount=1, scheduled=["pipeline.onSessionCompleted"]; identical outcome for status=expired, status=pending (no consent) and status=in_progress; status=completed returned {"alreadyCompleted":true} with nothing changed and nothing scheduled. Check B2: after the recruiter's cancel the row read 'cancelled', finish returned {"alreadyCompleted":false} and left status=completed, at which point convex/sessions.ts:278 refuses a second cancel. Check C: onSessionCompleted on that cancelled-then-finished session enqueued ["pipeline.transcribeSegment","pipeline.transcribeSegment","pipeline.transcribeSegment"] on mediaPool and set session.segmentsExpected=3, with no status precondition consulted.
- **Impact**: A lower-trust principal (token holder, no account) irreversibly overrides an owner/admin revocation: the session becomes 'completed', which sessions.cancel then refuses to touch, leaving only destructive deletion as recourse. The organisation pays for one transcription per previously uploaded answer plus one evaluation completion, the candidate's data retention is extended from the invitation clock to now + 365 days, project counters are falsified, and a report-ready email naming the candidate reaches the project creator and up to 200 organisation members. Bounded to one pipeline run per session and idempotent thereafter; no cross-tenant read or write.
- **Priority rationale**: likelihood medium — One call to a public mutation with the link token and no other precondition on the attacker's side; the candidate page already issues exactly that call from its final screen, so the same outcome occurs without any custom client when a cancellation lands while the candidate is finishing. It does require the recruiter to have cancelled, archived or left the role in draft first, which is an ordinary but not constant event. Overall medium (never above demonstrated impact medium). Confidence high.
- **Smallest source fix**: Make finish consult the same gate as every other candidate transition and forgive only the case the comment documents. Proceed when the gate is 'ready' or 'resumable', or when the sole blocker is the role's own expiresAt having passed on a still-active role; reject 'cancelled', 'closed' and a session whose own status is 'expired' by throwing the gate state, exactly as requireOpenSession does. Additionally require that the interview actually started (status 'in_progress' with consent), so a pending session that recorded nothing cannot be flipped to completed either. Cover it with convex-test regressions for the cancelled and the archived case asserting the row is unchanged and the scheduler empty.

### MEDIUM — The assessed candidate supplies the answer length that drives the recruiter report's para-verbal "measurements" and every quote anchor

- **Source location**: `convex/interview.ts:380` (entrypoint) → `convex/interview.ts:400` (propagation) → `convex/pipeline.ts:472` (propagation) → `convex/pipeline.ts:618` (propagation) → `convex/lib/reportBuilder.ts:87` (propagation) → `convex/lib/paraverbal.ts:159` (propagation) → `convex/lib/evidence.ts:106` (propagation) → `src/routes/app/$orgSlug/candidates.$sessionId.tsx:563` (sink)
